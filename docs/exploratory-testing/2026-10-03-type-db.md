## Journeys exercised

### 1. README quickstart and typed round trips on MySQL and PostgreSQL

Goal: a user following the README on MySQL or PostgreSQL gets the documented row shape, and each PHP scalar type round-trips.

- README create/insert/select and the scalar `select 1 as id, 'baz' as value`: correct `SqlInteger`/`SqlString` rows on MySQL (emulated and native prepares) and PostgreSQL.
- Typed table round trip (`bigint` at `PHP_INT_MAX`, `double` with `0.1 + 0.2`, UTF-8 text, NULL, `real`, `-0.0`, float equality in `WHERE`): correct on both servers.
- Variation, PostgreSQL `boolean`: `true`/`false` came back as `SqlNull` (**#72**).
- Variation, infinities and NaN: PostgreSQL rejected `SqlFloat(INF)` and the library rejected `SqlFloat(NAN)` with a SQLite-specific message. Raw PDO binds both, and the library reads both back (**#73**).
- Variation, DML result shape: PostgreSQL INSERT/UPDATE/DELETE returned `[[], []]`, while SQLite and MySQL returned `[]` (**#74**).
- Duplicate columns, unaliased expressions and named parameters behaved consistently with SQLite.

### 2. PDO attribute configurations across all three drivers

Goal: the hydration guarantees (NULL → `SqlNull`, numbers → `SqlInteger`/`SqlFloat`) hold under PDO attributes a user might already have set.

- `PDO::ATTR_CASE` with case-colliding aliases or joined columns (`select 1 as A, 'x' as a`; `t.ID` and `u.id`): duplicate-column detection fires correctly. **Rejected as a candidate**: I expected silent column loss, but the driver's metadata names are already case-folded.
- `PDO::ATTR_ORACLE_NULLS = NULL_TO_STRING`: NULLs in integer and real columns became `SqlInteger(0)`/`SqlFloat(0.0)` on SQLite and MySQL (**#75**).
- `PDO::ATTR_ORACLE_NULLS = NULL_EMPTY_STRING`: `''` becomes `SqlNull`. This is what the user asked PDO to do, so it is not a bug.
- `PDO::ATTR_STRINGIFY_FETCHES`: correct on SQLite. On PostgreSQL every numeric column stayed `SqlString`, and so did MySQL `tinyint`/`smallint`/`mediumint` (**#76**).

### 3. SQLite float rewriting after the v0.12.0 `SqlRewriter`/`QueryPlan` refactor

Goal: float parameters keep `REAL` storage and logical column names in SQL shapes not covered by earlier passes.

No defects. These all worked: reused `?1`; `?/2` and `?*?` next to the generated `/* */` marker; a `--` comment right after `?`; blob literals; `IN` lists; `COLLATE`; unaliased `? + ?`, `(?)` and `(select ?)`; upsert with `excluded.v + ?`; `RETURNING`.

## Unresolved candidates and observations

- **Float parameter echoed without a column** (`select ? as v` with `SqlFloat(1.5)`) returns `SqlString('1.5')` on MySQL and PostgreSQL. PDO has no float parameter type, and only the SQLite path adds a `CAST`. Values stored in typed columns round-trip correctly, so the only effect is on bare expressions. This is the non-SQLite counterpart of #19, but I could not ground the expected behaviour in documentation, so it stays unresolved.
- **PostgreSQL untyped parameters** (`select ? as v` with `SqlInteger(7)`, named `:a`) come back as `SqlString`, because PostgreSQL resolves untyped parameters to `text`. This is server semantics, not a library defect.
- **`numeric`/`decimal`** come back as `SqlString('12.50')` on MySQL and PostgreSQL. This keeps the precision and is a reasonable default.
- **Multi-statement SQL** on SQLite (`insert ...; insert ...`) runs only the first statement and gives no error. Raw `PDO::prepare` does the same. Usability observation: nothing tells the caller.
- **User alias containing the internal rewrite marker text** gets restored to `?`. This is contrived, so I am not reporting it as a bug.
- **Error mode**: failures on MySQL and PostgreSQL surface as raw `PDOException` under the default `ERRMODE_EXCEPTION`, which is already tracked in #71.

## Blocked or unexplored

- MariaDB, ODBC and dblib were not tested.
- MySQL `ATTR_STRINGIFY_FETCHES` was only checked for integer and float types. Date, time and `YEAR` were not.
- Transactions and long-lived connections were not exercised.
