# Exploratory testing report: SQLite consumer journeys

Date: 2026-10-31. Tested `origin/main` at `5d952bbbb709e90e43a104f27246edf2f948c8e5`.

## Environment and setup

The pass used the public PHP API with PHP 8.5.4, PDO SQLite, and SQLite 3.46.1. Composer installed the committed lockfile in a separate worktree with `composer install --no-interaction --no-progress --prefer-dist`. The consumer script used a fresh SQLite file for each run and removed it after each run. No server, browser, container, image, or volume was started.

The baseline suite reported 196 tests, 420 assertions, and 13 skips. PHPStan reported no errors. PHPAssumptions reported 0 assumptions in 110 expressions. The skipped tests include server-dependent cases, so the baseline does not establish PostgreSQL behavior.

## Journeys

Each journey ran three times from a fresh database. The [consumer script](evidence/2026-10-31/journeys.php) records the exact calls. The [output](evidence/2026-10-31/journeys.txt) records all three runs.

1. **Create and reopen data.** A consumer creates a table, inserts two rows through `Connection::quickQuery()`, and selects them with positional parameters as in the README. Both expected rows returned. After reopening the database, the rows, a float value, and a null remained present.
2. **Bind parameter variations.** A named float bound by name returned `1.5` with SQLite storage class `real`. Numbered positional parameters returned the expected float and string in the requested order. A float supplied positionally to a named placeholder returned string `"1.5"` with storage class `text` on all three runs. This reproduces [issue #36](https://github.com/jonbaldie/type-db/issues/36), which already requests rejection of mismatched binding styles. No duplicate issue was filed.
3. **Recover from a failed write.** With `PDO::ERRMODE_SILENT`, an insert with a duplicate primary key threw `RuntimeException`. The table still contained two rows. A corrected update succeeded and its value remained after reopening the file.

## Confirmed existing issue

[Issue #36](https://github.com/jonbaldie/type-db/issues/36) tracks positional values supplied to named SQLite placeholders. A fresh database is not needed to reproduce it. Create a `Connection` over `sqlite::memory:`, then call `quick_query($connection, 'select :amount as amount, typeof(:amount) as kind', [to_sql(1.5)])`. Named binding returns a float with `real` storage; positional binding returns a string with `text` storage. A consumer who mixes the styles can silently lose the float type. The issue's current triage direction is to reject that mismatch, rather than support the mapping.

## Observations and limits

- No new confirmed bugs or unresolved candidates were found in these journeys. The report does not claim that the API is free of other defects.
- The parameter mismatch is easy to miss because SQLite accepts the binding and returns a result. The matching named form works in the same script.
- [Issue #23](https://github.com/jonbaldie/type-db/issues/23) already rejected a negative-zero storage report as an SQLite engine constraint. This pass did not reopen it.
- MySQL, MariaDB, PostgreSQL, other PDO drivers, transactions, concurrency, and other PHP versions were not exercised. The local PHP installation has no PostgreSQL PDO driver, and no external database server was provisioned for this SQLite-focused pass.
- The script compares visible returned values and SQLite storage classes. It does not exhaustively test binary float precision or all placeholder combinations.

## Replay

Install the lockfile dependencies, then run `php docs/exploratory-testing/evidence/2026-10-31/journeys.php` from the repository root. The script creates and deletes uniquely named scratch database files beside itself.
