## Journeys exercised

### 1. Type round-trips, boundary conditions, and schema storage class fidelity

Goal: evaluate type fidelity and lossless conversion for all supported types through `to_sql()`, `from_sql()`, and `quick_query()` against boundary inputs.

Inputs tested:
- Strings: empty string `""`, strings containing single and double quotes, newlines, tabs, binary NUL bytes (`"\0"`), multi-byte UTF-8 and 4-byte astral characters (e.g. `résumé`, `ñoño`, `🚀`, `日本語`, `𠜎`), SQL injection fragments, and strings up to 100,000 characters.
- Integers: `PHP_INT_MIN`, `PHP_INT_MIN + 1`, `-1`, `0`, `1`, `PHP_INT_MAX - 1`, `PHP_INT_MAX`.
- Floats: `PHP_FLOAT_MIN`, `PHP_FLOAT_MAX`, `PHP_FLOAT_EPSILON`, `0.0`, `-0.0`, `1.0`, `-1.0`, `3.141592653589793`, `1.5e-300`, `1.5e300`, `INF`, `-INF`.
- Special: `NAN` properly rejected with `InvalidArgumentException`.
- SQLite storage classes: verified dynamic columns (`CREATE TABLE t (v ANY)`) preserving storage classes (`SqlString`, `SqlInteger`, `SqlFloat`, `SqlNull`) row-by-row without coercive decay.
- Declared column affinities: verified that `NUMERIC`, `DECIMAL(10,2)`, `BOOLEAN`, and `DATETIME` columns preserve cell storage classes under default and custom fetch modes.

Result: passed.

### 2. SQL syntax, parameter forms, and query construct invariance

Goal: verify metamorphic invariants and query behavior across diverse SQL constructs:
1. Positional parameter forms: anonymous `?`, numbered `?NNN`, mixed sequential numbering, and reuse (`?1`, `?2`, `?1`).
2. Named parameter syntax: colon parameters (`:name`), numeric named parameters (`:1a`), namespace parameters (`:ns::param`), and array-index parameters (`:arr(key)`).
3. Query constructs: math functions (`abs(?)`, `round(?, 1)`), `CASE` expressions, `UNION ALL` combining integer and float rows across columns, subqueries, and table creation/mutation (`CREATE TABLE`, `INSERT`).
4. Duplicate column detection on unaliased parameters: verified that unaliased parameter reuse (e.g. `SELECT ?1, ?1` or `SELECT :x, :x`) throws `RuntimeException` for duplicate column names.

Result: passed under default connection configuration (`PDO::CASE_NATURAL`).

### 3. Driver configuration stateful testing (`PDO::ATTR_CASE`)

Goal: evaluate TypeDb against custom driver configurations commonly used by application frameworks, specifically column case normalization via `PDO::ATTR_CASE` (`PDO::CASE_LOWER` and `PDO::CASE_UPPER`).

Result: defect found ([#51](https://github.com/jonbaldie/type-db/issues/51)).
- While commit `7ceeabb` addressed internal rewrite token leakage by making rewrite replacement case-insensitive in `sqlite_result_column_name()`, the replacement callback inserts `$rewrite['original']` verbatim.
- As a consequence, unaliased named float parameter column names retain the raw casing from the SQL query instead of conforming to `PDO::ATTR_CASE`:
  1. Under `PDO::CASE_LOWER`, unaliased queries with uppercase named parameters (e.g. `SELECT :PARAM`) return uppercase keys (`':PARAM'`), violating `CASE_LOWER`.
  2. Under `PDO::CASE_UPPER`, unaliased queries with lowercase named parameters (e.g. `SELECT :param`) return lowercase keys (`':param'`), violating `CASE_UPPER`.
  3. Column name invariance between `SqlInteger` and `SqlFloat` is broken: for `SELECT :PARAM`, binding `SqlInteger` yields `':param'` under `CASE_LOWER`, while binding `SqlFloat` yields `':PARAM'`. Symmetrically under `CASE_UPPER`, `SELECT :param` yields `':PARAM'` for integer and `':param'` for float.
  4. Duplicate column validation in `statement_duplicate_column_names()` is completely bypassed when selecting two columns that differ only in casing where one is a float and the other is an integer (e.g. `SELECT :param, :PARAM` with integer and float parameters). Both columns are returned in the result row instead of throwing the expected `RuntimeException`.
